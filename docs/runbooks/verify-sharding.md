# Verify job sharding

This workflow change ships independently of daemon PID identity PR #354. It does not change product code, product/protocol test assertions, platform coverage, job timeouts, or repository permissions. The first hosted run failed at two job limits. The second round expands only the approved CI topology policy expectations; its budget remains unverified until measured.

## Execution and ownership

`package.json` keeps the original local `verify` command byte-for-byte. `verify:pre` and `verify:post` are exact projections of the commands before and after its main `bun test --timeout 60000`. `verify:ci` owns `scripts/verify-ci.mjs`; `.github/verify-sharding.json` owns active scheduling weights and the four split targets. The weights are not a test whitelist.

Only the measured timeout legs, macOS15/Node24, macOS15/Node25, Windows/Node22.22 and Windows/Node25, receive three whole-file test jobs. The other five OS/Node combinations retain one complete verifier. Each test job gets its own checkout, Bun process, and real temporary daemon/SQLite fixtures. Tests within a file remain sequential. No shared fixture, concurrent test mode, mocked protocol replacement, or platform skip is introduced.

The split dependency graph is **pre → all test shards → coverage proof → post**. Matrix dependencies may delay a healthy target when another split target is slow; queue time is not a job timeout or a reduction in billed runner time.

## State and gate order

The pre job preserves Windows ACL regression → platform IPC readback/upload → all original pre-gates, in order. It then builds the native Bun discovery plan. Ubuntu22's network-isolated E2E and upload stay on its unsplit worker. Governance and Linux arm64 checks are unchanged.

The post job waits for every test shard, validates exact file coverage, then executes all original post-gates in order: explorer, full packaged CLI smoke, privacy checks, committed readbacks, acceptance ledgers, sprint status, and evaluations. It does not run the native-only smoke in place of the full smoke.

No test machine state is migrated. The pre CodeGraph Node-selector gate creates and removes its own fixture and bundle under a temporary/cache directory. Test files likewise own their temporary state. The post explorer check reads source and constructs its own benchmark data; the packaged CLI script builds a new native bundle and creates a fresh Git/daemon/SQLite fixture from its local dependency install. Privacy/readback/acceptance/sprint/eval gates read committed inputs. They do not consume test SQLite, runtime connections, JUnit, or bundles produced by another machine. Dependencies and platform bindings are installed again on each post runner. Only the discovery plan and test inventory/JUnit metadata cross jobs.

## Discovery and coverage

The pinned Bun1.4.3 runner performs its real discovery with an impossible test-name pattern, writing a **fresh native timing inventory**. This metadata-only process executes module registration but no test bodies. Its documented-by-fixture no-match exit is accepted only for this inventory operation; import/evaluation failures are rejected. The inventory includes files with no registered tests. It respects Bun's own patterns, exclusions and path handling rather than duplicating them in a glob.

The controller balances all currently discovered paths using the historical cost weights, assigning an explicit default scheduling weight to newly added paths and ignoring weights for deleted paths. Each shard executes unfiltered, exact file arguments through `spawn` argument arrays, so spaces are preserved. Its measured timing inventory starts empty and is never seeded with weights. An empty planned shard writes an explicit zero-file report and never launches an accidental unfiltered full suite.

The coverage gate checks subject (`run ID`, `attempt`, checkout SHA), target, every expected shard including empty ones, zero exit status, assigned versus actually executed paths, pairwise disjointness, and union equality with real Bun discovery. Missing, duplicate, foreign, stale, failed or omitted-file reports fail. Plan/shard artifacts include the attempt in their name.

The nine final required-check names remain `OS / Node version`, as required by the live FG6 reader. IPC artifacts retain `platform-ipc-permission-OS-node-version` and are produced exactly once per target on the actual OS runner. The collector and summaries use `always()`. The collector reads all pages of the current attempt's GitHub job API and checks every expected execution job individually for a unique name, completed/success conclusion, and matching run/attempt/head. A missing, skipped, cancelled, failed, duplicated or cross-subject job fails its target. An API failure fails all summaries. Matrix rollup success alone is never sufficient. Existing workflow permissions remain `contents: read`.

## Approved four-target second round

The same three-shard mechanism now also covers macOS25 and Windows22. There are **25 execution jobs**, **27 installs** including Governance/arm64, and **39 total jobs**. Relative to round one this adds eight jobs and eight installs, rather than multiplying all nine targets. At the measured macOS25 install time of 13 seconds and Windows22 time of 31 seconds, the new repeated-install component is `4 × 13 + 4 × 31 = 176 seconds`, or **2.93 raw runner minutes**. Other repeated checkout/setup/artifact work and finishing previously cancelled gates add further cost.

Mapping Windows22's completed per-case timings onto the unchanged whole-file buckets gives **18.99/18.90/17.54 minutes** of test work; their 55.44-minute sum excludes some registration/teardown time from the 55.87-minute native summary. Plan around **20–25 minutes per Windows22 shard job**, including setup. For macOS25, plan around **10–13 minutes per shard job**, allowing for its unobserved tail beyond the partial 7.25-minute maximum. These are planning estimates, not bounds or measured second-round results. All execution jobs retain the existing **20/60-minute caps**. End-to-end wall clock also includes pre/post stages and matrix-wide queues; it is not the longest individual shard.

For total runner planning, round one's 282.87 plus the new 2.93-minute install component is **285.80 minutes before** further setup and unfinished work. A provisional **295–310 raw runner minute** envelope reserves approximately 9–24 more minutes for those components under similar runner speeds. The macOS25 tail was not measured, so the envelope is an explicit assumption, not a guaranteed upper bound or a cost-saving claim. The next run must measure its actual total, installs and individual caps before any budget acceptance. Governance deduplication contributes no assumed saving here.

`Verify runner cost` waits for all nine summaries plus Governance and Linux arm64, then publishes `verify-runner-cost-attempt-N/runner-minutes.json` and a job summary containing total completed raw runner minutes, the sum of per-job rounded minutes, OS totals derived from actual runner labels (not summary names), completed dependency-install count/time, and elapsed time at the sample. The reporting job's remaining cleanup/upload time is explicitly unmeasured. `verify-job-evidence-attempt-N` separately records the exact branch head/run/attempt and each target's actual job verdict. The final first-round totals above were read after all jobs terminated, including the cost reporter's tail.

## Governance pressure and deferred proposal

Governance is unchanged in this PR. Its first-round job passed in **13.80 minutes** against a 15-minute cap: the full verifier took **805.696 seconds**, and the other 23 inspections together took **0.803 seconds**. The same candidate's Ubuntu22 matrix full job took **9.77 minutes**, so duplicating full verification and runner-speed variation can consume Governance's margin. The remaining unsplit macOS22 and Windows24 jobs passed in **16.73/52.48 minutes**, leaving 3.27/7.52 minutes against their unchanged caps; this round does not establish future speed guarantees.

On #356's **old HEAD**, Governance job 116107408283 lasted exactly 15 minutes, 21:12:22–21:27:22 UTC. The verifier reported verified/ok at 21:27:19, all 24 commands exited zero, and cleanup succeeded at 21:27:20. Its main suite had 3125 pass / 4 skip / 0 fail; the full verifier took 880.975 seconds and the other 23 inspections 0.842 seconds. This supports a final-wrap-up timeout, not an assertion failure. It is separate historical evidence and is not a result for this candidate.

A separately approved follow-up could reuse the identical successful Ubuntu22 full-verifier evidence for automatic Governance, then execute all 23 inspections. It would need canonical command descriptors, script digests, exact checkout/run/attempt/runtime identity, genuine producing-job success, and a machine check that the reused verifier plus inspections equals the current ordered 24-command set. Manual revalidation has no matrix and would need its own isolated pre/shard/post verification before inspections. Local `verify:governance` would retain all 24 commands. Dependency waits must occur before runner allocation. Potential duplicate-work savings are about 13.43–14.68 raw runner minutes in these samples, before any new overhead. **This authority/receipt change is not approved or implemented in this round.**
