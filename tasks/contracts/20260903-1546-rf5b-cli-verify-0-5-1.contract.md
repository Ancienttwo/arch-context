## Why

RF4 lands `refactorVerify` and the resolve lookup inside the daemon, but no caller can reach it and repo-harness gates its `active` mode on `refactor-resolution-v1` appearing in `capabilities --json`. Without this row the measure → record → verify loop stays daemon-internal and 0.5.1 cannot ship.

## Goal

Add `RefactorVerificationRequestV1` + `REFACTOR_VERIFICATION_REQUEST_SCHEMA_VERSION` + `refactorVerificationRequestInvariantIssues` to `packages/contracts/src/refactor.ts` (append-only; no existing export changes) and make RF4's `RuntimeRefactorVerifyInput` a type alias validated at RPC ingress. Add CLI `archctx refactor verify --request-json <json> [--json]` (flag required; missing/malformed → `AC_SCHEMA_INVALID`; thin adapter over `refactorVerify`; no envelope post-processing) with one help example. Add `refactor-resolution-v1` to `ARCHCTX_FEATURES` (sorted), the capabilities schema enum and fixture. Bump the product to `0.5.1` everywhere (product-version.ts, root + 5 workspace manifests, bun.lock workspace entries, product-version-manifest fixture, catalog.yaml productVersion + regenerated catalogDigest via the repo scripts, review action, docs/spec.md Release State, runbook, both docs/examples). Regenerate the three no-LLM readbacks (fg4 deterministic-conclusion → fg6 no-provider-deterministic → fg6 organization-runner-no-llm) with their `run` scripts. Extend packaged-cli-smoke with record → verify (or the documented rejection if no recordable recommendation). Add `deploy/release-checklists/archctx-0.5.1.md` skeleton (unticked).
